# Printer Nanny — audit, July 2026

> **HISTORICAL SNAPSHOT — not a backlog.** Audited at central **0.5.0**; the
> codebase is now **1.0.x**. All six P0 findings and most of P1 are fixed. For
> what is actually outstanding, read **`docs/completion-playbook.md`**, which
> also records which of these were verified fixed.

Audited at **central 0.5.0 / agent 0.5.0** (commit `45cbce7`), 30,114 Python
LOC, 690 tests. Findings were produced by parallel review agents and then
**re-verified by hand** before being written down; anything that could not be
confirmed in the source is marked as such.

## Verdict

This is not a half-built product. The spine is genuinely good: durable
per-channel delivery with exponential backoff and dead-lettering, Postgres
advisory-lock leader election, race-safe report idempotency, refill-aware
supply forecasting, Fernet encryption at rest, a real audit trail, and a test
suite with substantive authz and concurrency coverage.

What is immature is everything that turns observation into action, and one
theme dominates: **the system fails silently in at least five independent
places**, each of which looks identical to healthy operation.

| # | Silent failure | Status |
|---|---|---|
| 1 | A dead printer is never detected | **Fixed** (0.6.0) |
| 2 | A logo upload disables every channel and STARTTLS | **Fixed** (0.9.1) |
| 3 | Zero routed channels ⇒ alert lost forever, no trace | **Fixed** (0.10.0) |
| 4 | A dead worker is undetectable and self-camouflaging | **Fixed** (0.9.0) |
| 5 | Total agent SNMP failure reports green | Open |

### 1. A dead printer never produced an alert — *fixed, 0.6.0*

`PrinterStatus.offline` existed in the enum and was read in three places
(`queries.py:210`, `routes.py:313`, `reports.py:140`) but **written by
nothing**. An unreachable printer raises inside `poll_one`, is dropped from the
batch, and central is never told; since `Printer.status` is only ever written
from an arriving reading, it kept its last-good value. Unplug a printer and it
read "ok" forever. Only whole-agent outages were detected.

`agent/printer_nanny_agent/oids.py:75` even asserted that "offline detection is
handled centrally via missed heartbeats / stale last_seen" — the `last_seen`
half was never built.

Fixed with a `mark_offline_printers` job plus a `printer_offline` alert
condition. Printers behind an offline agent are deliberately skipped in both,
so a site outage stays one alert instead of one per printer.

### 2. Identity keyed on IP, not serial — *fixed, 0.7.0*

`serial` was stored and never used as a match key. DHCP churn broke both ways:
a moved printer became a duplicate row (page meters then double-counted across
the two, corrupting billing), and a *different* printer inheriting a recycled
IP silently adopted the old row's id, history, meters, asset tag and
maintenance records.

This is the one finding every competitor confirms by counter-example: ECi keys
on manufacturer+serial, shipped serial-only first, hit cross-manufacturer
collisions, and *still* ships an auto-merge utility.

Fixed by preferring serial, scoped to the agent's sites, with IP as fallback.
The `uq_printer_site_ip` UNIQUE constraint had to go: under the new model a
replacement device and the one it replaced both reference the same address, so
UNIQUE could only be satisfied by merging their histories — the exact
corruption being prevented.

### 3. Tech-role account → RCE on every site agent — *fixed, 0.8.0*

`POST /api/v1/commands` was gated by `require_staff` (admin **or** tech),
`CommandIn.payload` was unvalidated, and the agent fed `payload["pip_source"]`
to `pip install --force-reinstall` as root/LocalSystem. See the 0.8.0 commit
for the full chain and the three-layer fix.

## Open — ranked by (operational value ÷ effort)

### P0

**`save_settings(sections=None)` silently disables every channel and STARTTLS**
— `runtime.py:299`. `value = spec.key in form` treats *absent* as *unchecked*
for every bool spec. Five callers pass no `sections`, including
`auth_oauth_smtp.py:148`, which fires on every OAuth SMTP token refresh
(roughly hourly, unattended). Effect: `smtp.use_tls` → False (SMTP password
then sent in the clear), plus every channel `enabled` flag, `oidc.enabled`
(SSO lockout) and `scim.enabled` flipped off. Credentials survive, so Settings
still *looks* configured. **Trigger: uploading a logo.**
*Fix:* `if spec.type == "bool" and sections is None and spec.key not in form: continue`. **XS.**

**Zero routed channels ⇒ the alert is lost permanently** — `delivery.py:146-157`.
`dispatch(note, [])` returns `[]`, so no `NotificationDelivery` row is written
and `retry_due` has nothing to find. The alert is now open, so dedupe
suppresses all future attempts — re-enabling the channel does not recover it.
Compounds directly with the above. *Fix:* persist a `pending` row when the
channel list is empty. **S.**

**A dead worker is undetectable** — no job records a last-run timestamp in any
of the 21 tables, and `/healthz` (`main.py:47`) returns static `{"status":"ok"}`
— verified to return 200 with the database unreachable. Because
`mark_offline_agents` is itself a worker job, a dead worker also stops marking
agents offline: the dashboard shows a green fleet with frozen data. *Fix:*
stamp `last_success_at` per cycle, add `/readyz` returning 503 on stale-or-DB-down,
wire compose healthchecks. **S.**

**Brother alert parsing invents "toner empty" from unrelated conditions** —
`providers/brother.py:84-88`. The trailing colour group `(?P<color2>BK|K|C|M|Y)\s*$`
has no `\b`, so the last letter of any word becomes a colour code. Verified:
`"Replace Drum"` → magenta toner 0.0%, `"No Paper"` → black 0.0%,
`"Out of Memory"` → yellow 0.0%. That 0.0 flows into a low-supply alert, a
FreeScout ticket and a supply order for a printer that is out of *paper*.
*Fix:* require toner context in the regex and anchor the colour group. **XS.**

**Central outage stops polling entirely** — `runner.py:345-364`. The heartbeat
and `poll_targets` share one `try`, so a central restart loses every reading
for the window rather than spooling it — defeating the spool in precisely the
scenario it was written for. **S.** *(In progress.)*

**SNMPv3 polling is non-functional** — `runner.py:86-94`. `_params_for_target`
builds `SnmpParams` with no `v3_*` fields and no `bind_interface`, while
discovery correctly uses `config.snmp_for(subnet)`. A v3 subnet sweeps fine,
then every poll fails auth forever. Dropping `bind_interface` also breaks the
documented multi-client bind-IP pattern. **S.** *(In progress.)*

### P1

  `alerts.supply_deadband_pct` + flap cooldown `alerts.renotify_cooldown_min`.)*
  `jobs.py:299` opened at `<=` and resolved the
  moment it isn't. A cartridge oscillating 9↔11% around a threshold of 10
  produced 3 fresh alerts in 6 cycles — 720 notifications/day at the 60s
  interval. **M.**
- ~~**Only the newest error code is tracked**~~ *(Fixed, 0.11.0 — one alert per
  distinct code, capped and disclosed.)* `jobs.py:317-319`. A newer
  `DOOR_OPEN` auto-resolved an unresolved `PAPER_JAM`; the inbox said the jam
  was fixed while the printer was still jammed. **S.**
- ~~**Acknowledged reorder alerts stick open and suppress all future ones**~~
  *(Fixed, 0.11.0.)*
  `jobs.py:754` filtered `state == open` while every sibling uses `_LIVE_STATES`.
  One-token fix. **XS.**
- **`alembic upgrade head` crashes on any `DATABASE_URL` containing `%`** —
  `migrations/env.py:16` routes the URL through ConfigParser interpolation.
  The line is redundant (line 37 already injects it). Any percent-encoded
  password kills the api container's startup migration while the app itself
  boots fine — a permanently unmigrated schema with no obvious symptom. **XS.**
- ~~**Teams sends nothing and reports success**~~ *(Verified fixed — `teams.py`
  now reads `self.config` first, with env only as a fallback.)* **XS.**
- ~~**Every dry-run / severity-skip path returns `ok=True`**~~ *(Fixed, 0.11.0 —
  `ChannelResult.sent` splits "nothing failed" from "nothing was sent"; non-sends

  `delivery.py:109` recorded them as `delivered` and the UI rendered a green ✓ —

- ~~**Escalation orphans the FreeScout ticket**~~ *(Fixed, 0.11.0.)*
  `jobs.py:166` assigned

- **One bad supply level rejects a whole batch forever** — `schemas.py:42`
  uses `Field(ge=0, le=100)` where `_sane_meter` elsewhere coerces. With the
  spool, the poisoned batch re-sends every cycle and never drains. **S.**
- **Monthly billing CSV emits lifetime cumulative meters, not period deltas** —
  `reports.py:203-219`. Correct, reset-safe delta code exists in

- **Customer portal under-reports open issues** — `routes.py:185-188` takes the
  newest 30 alerts *fleet-wide* then filters by tenant, so a customer sees "no

- **No CSRF tokens**, and `GET /admin/backup/download` (`backup_routes.py:123`)

- **`admin`/`admin` recreated on every container start** with no forced

- **Third-party CDN scripts with no SRI and no CSP** — `base.html:7-8`. Also

### P2 — scale and hygiene

- **No readings retention, rollup or partitioning.** ~52M rows/year at 500
  printers. Two docstrings (`models.py:394`, `db.py:52`) claim monthly
  partitioning that migration `0002` explicitly deferred and never built.
- **21 unbounded dashboard queries**; `per_client_rollup` is 5N+1 (~1,001
  queries at 200 clients); `/manage/audit` caps at 200 rows with no offset, so
  at 100k rows 99,800 are permanently unreachable.
- **`retry_due` has no LIMIT and no ordering** — one SMTP outage can stall the
  whole worker cycle under the leader lock.
- **DB-row channels never retry** — `delivery.py:197` rebuilds from globals
  only; a name collision can retry a client-scoped channel to the global
  webhook, leaking cross-tenant.
- **Migration downgrades drop tables their upgrade didn't create** (`0003`,
  `0007`, `0012`, `0014`, `0019`) — on a pre-Alembic install, `downgrade 0002`
  deletes every operator setting including SMTP credentials.
- **CI cannot detect model/migration drift**: `0001_baseline` is
  `create_all` against *current* metadata, so a fresh chain gets today's schema
  whether or not later columns have migrations — the check passes by
  construction. CI also has **zero Postgres**, so the BRIN index, advisory-lock
  leader election and `pg_dump`/`pg_restore` paths are the only ones that run
  in production and the only ones never tested.
- **`deploy/Dockerfile:16-20`** falls back to a hardcoded install list that
  **omits `authlib` and `cryptography`**, then `|| true` swallows failure — the
  image can build green and 500 on SSO.

### Observability and UX

Scored 1/5 and 2/5 respectively, and they compound the silent-failure theme.

- No metrics, no request IDs, no error tracking. `central/main.py` never
  configures logging, so **all 11 `log.info()` sites in `central/` are silently
  discarded in the API container** and warnings emit with no timestamp or
  logger name.
- **No fleet-wide printer list and no printer search anywhere.** A tech handed
  "10.4.7.23 is jamming" must already know the client.
- **Nothing live-updates** (no HTMX polling, SSE or WebSocket) and no "data as
  of" timestamp — a NOC screen shows a green fleet that has been on fire for
  hours, authoritatively.
- Flash messages are never popped in `routes.py:_render`, so errors raised in
  `manage.py` are **never displayed**; `base.html:47` styles all flashes green,
  so errors would render as success anyway.
- Three tables use `overflow-hidden`, making Approve/Resolve **physically
  unreachable on a phone**. 46% of form controls have no programmatic label;
  zero ARIA; several sub-3:1 contrast pairs. `dark:` variants: 0.
- Dead-lettered alerts have **no UI at all** — `NotificationDelivery` appears
  in zero routes and zero templates.

## Competitive position

**Research caveat, stated plainly:** the egress proxy blocked essentially every
vendor domain (403 at CONNECT) and the web-search budget was exhausted, so **no
primary vendor document was retrieved**. Open-source findings are solid (GitHub
was reachable, so they come from actual source). Commercial vendor claims are
second-hand from search snippets and should be re-verified before being used
commercially.

### Where Printer Nanny already wins

- **There is no credible open-source competitor.** A GitHub sweep returns
  essentially one comparable project (`mstrhakr/printmaster`, MIT, ~9 stars).
- **Nothing in open source forecasts supply depletion.** Zabbix has
  `timeleft()` but no printer template uses it; Prometheus's `predict_linear()`
  breaks across cartridge swaps; Checkmk's "predictive levels" are seasonal
  baselining, not depletion. The forecast is a genuine differentiator.
- **Self-hosted and data-sovereign.** Printanista and MPS Monitor are
  cloud-only.
- **True multi-tenancy** including the cross-client HQ-bridge pattern. Checkmk's
  `customer` object is the only comparable model in mainstream monitoring, and
  it needs the top tier plus distributed monitoring.
- **Read-only SNMP is strategically safe.** HP's "Secure by Default" (FutureSmart
  4.5+) disables SNMPv1/v2 **writes** while explicitly keeping **reads** — the
  most aggressive OEM hardening in the market leaves this product working.
- Per-device fee: none, against an incumbent with a documented price-shock
  history.

### Table stakes still missing

1. **Cost-per-page / TCO reporting** — the core MPS commercial artifact, and
   how this industry prices. Absent entirely.
2. **Remote EWS access through the agent** — shipped by ECi, MPS Monitor, HP
   SDS, Sharp, and even the 9-star OSS competitor. Removes the truck roll.
3. ~~**Alert suppression, quiet hours, maintenance windows**~~ *(Shipped, 0.12.0 —
   `central/suppression.py` + `suppression_windows`: recurring client-local quiet
   hours and one-off UTC maintenance ranges, per-window break-through floor,
   defer-then-digest or drop.)* Previously none existed (exhaustive grep). This
   was the loudest complaint in the field.
4. **Occurrence-rate alerting** — "not every jam, but 10 jams/day".
5. **Utilization / right-sizing analytics** — the consultative MPS sell.
   Pharos's definition is the implementable one: utilization is a *cost-optimum
   curve*, where 100% is the balance between amortizing fixed costs and
   over-driving a device — not a duty-cycle ratio.
6. **Server-pushed device/model definitions**, so new models don't require an
   agent release. ECi's MDF release feed is on page 69 — that is the
   maintenance burden being externalized.
7. **Supply ordering with SKU mapping** and shipment consolidation.
8. **PSA integrations** (ConnectWise, Autotask, HaloPSA). *The clearest open
   ground in the market* — incumbents are welded to e-automate, a dealer ERP,
   while MSPs live in ConnectWise/Halo.
9. **Collector redundancy.** PrintFleet's own blog: *"on average, in the SMB
   market, 10–20% of DCAs stop working at some point in time."*

### Calibration points worth copying

- Xerox ASR orders at **2–3 weeks of usage remaining**, targeting one month on
  hand. Xerox XDA supply alerts are configurable **0–20 days**. Konica Minolta
  dispatches at **20% remaining**.
- MPS Monitor triggers replenishment on **level OR days-remaining OR
  pages-remaining**. Pages-remaining is cheap here — page counts are already
  collected.
- LibreNMS ships **58 alert transports** (vs five here) and logs *"Toner X was
  replaced"* when a level **rises** — cheap, and the signal that makes yield-gap
  analysis possible.
- Checkmk's `printer_alerts.py` decodes **80+ `prtAlertCode` values** to states
  — a ready-made benchmark for a richer alert taxonomy.

### Xerox's weakness is the sharpest differentiator

Xerox Device Agent's supply alert thresholds **cannot be edited**. Alert
escalation, suppression, business-hours awareness and correlation could not be
found in *any* OEM tool surveyed. That is white space.

*As of 0.12.0 three of those four are now shipped here: escalation
(`alerts.escalate_after_minutes`), suppression + business-hours awareness
(quiet-hours windows, read in each client's local time). Correlation is still
open — the nearest thing is the per-error-code alert cap from 0.11.0.*

## Corrections to earlier assumptions

- **MPS Monitor was acquired by Valsoft (Sept 2022)**, not Canon/NT-ware.
- **"Printanista Ops", "Printanista Fleet", "PrintFleet Vault" do not exist.**
  The real line is Printanista **Hub** + **Workflow**.
- **HP Web Jetadmin is not EOL** — SR11 shipped 05/2026, despite a distributor
  feed claiming October 2025.
- **PaperCut is not the competitor it appears to be.** Its own docs direct you
  to Zabbix/PRTG/Nagios for device health, and its per-user licensing is
  structurally misaligned with per-device MSP economics. But **PaperCut Views
  gives away supply forecasting for free**, and Vasion Insights gives away
  SNMP status + alerting for 10 devices — that is the free-tier floor.
