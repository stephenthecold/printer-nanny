A definition is data, never code. It names OIDs and states, in a fixed vocabulary, how to turn each answer into a supply level, a meter or a status message. Agents fetch the set on every poll, cache it locally, and re-validate it themselves — an agent that cannot reach this server keeps working exactly as it did before.

{{ c.section_title("What a definition may say") }}

match — at least one of enterprise (the sysObjectID enterprise number), brand or model (case-insensitive substrings, minimum 3 characters). A definition with no criteria is refused: it would be applied to every printer in every client. The most specific match wins, and an exact tie is refused rather than guessed.

supplies — each names an oid, a type (toner, ink, drum, fuser, waste, staples, developer, other), an optional color, and a decode.

decode — one of:

  • {"kind": "percent"} — the value is already 0–100.
  • {"kind": "ratio", "max": 30000} or "max_oid" — a remaining/total pair.
  • {"kind": "map", "values": {"1": 100, "2": 50}} — exact sentinel to percentage.
  • {"kind": "text_between", "after": "Toner:", "before": "%"} — literal delimiters.
  • {"kind": "count"} — a meter reading.
There are no regular expressions, and there will not be. A pattern supplied here would run on every agent in the fleet, and a catastrophically backtracking one would stall all of them at once — with no way to tell in advance which patterns those are. text_between slices between two literal strings, which is linear whatever you type. A definition carrying regex/pattern is refused with that reason.

meters — total, mono, color, or any function name (print, copy, fax) which lands in the meter snapshot. status_text and identity fill the front-panel message, the brand tag and a more precise model.

Use printer-nanny-agent probe <ip> against the device to get the OIDs and the raw values to write these against.
