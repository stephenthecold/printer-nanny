{# Shared UI components. WHY THIS FILE EXISTS -------------------- Before it, the same four elements were spelled many different ways across 23 templates: 30 distinct button class strings (two competing "primary" colours, padding ranging px-2..px-5 / py-0.5..py-2.5, hover states on some and not others), 30 card variants, 9 heading variants and 20 table-header variants. Nothing was wrong on any single page; the drift only showed up when operators moved between pages. Centralising the class strings makes "what does a primary button look like" answerable in one place instead of by grep-and-vote. HOW TO USE IT ------------- Import what you need at the top of a template: {% from "_components.html" import btn, page_title, field %} The class-string macros (btn, card_cls, th_cls, input_cls) return *classes*, not elements, because nearly every control here also carries hx-* attributes, name=, formaction= or a confirm handler. Returning classes keeps those explicit at the call site instead of forcing every attribute through a macro signature. The structural macros (field, page_title, empty_row) do emit elements, because their whole point is to make a repeated *structure* consistent -- particularly the label/control pairing.
